# Asset Provenance Workflow (Phase 5B)

How a Gemini-generated image is recorded, reviewed, accepted or rejected — and what FandomVerse does and does not claim about it.

Applies to every asset in Tier B/C of `ASSET_MANIFEST.md`. Current status: **no asset has entered this workflow.** No image has been generated.

---

## 1. The claim we do not make

> **Generated output is not assumed to be copyright-free, public domain, or unencumbered.**

This is the central rule of this document, and it exists because the opposite assumption is common and wrong.

What we can state truthfully today:

- The image was produced by Google Gemini from a prompt authored in this repository.
- The prompt, the generating tool, and the date are recorded.
- The prompt was written to avoid third-party IP, and the result was human-reviewed against an IP checklist.
- FandomVerse is a non-commercial student/competition project.

What we **must not** write in `08_LICENSES.md` or anywhere else:

- ❌ "Public domain"
- ❌ "Copyright-free"
- ❌ "No license required"
- ❌ "We own the copyright"
- ❌ "Royalty-free"
- ❌ Any specific licence name that has not been read and verified against Gemini's actual terms on the generation date

The correct register is **`AI-generated — generated by Google Gemini on <date> from a prompt authored in this repository; usage governed by the generating platform's terms as of that date; ownership status not independently adjudicated.`**

If the platform's terms cannot be established at generation time, the asset's status is `Pending Verification` and **it does not enter the repository** (`00_PROJECT_CONSTITUTION.md` §10: nothing is used on the assumption that it's "probably fine").

### Why this matters more than usual here

Phase 5's 161 procedural SVGs have genuinely unambiguous provenance — they are output of a script in this repository, reproducible byte-for-byte (D-036). Introducing generated imagery is the first time FandomVerse takes on an asset whose rights position is *not* fully self-evident. That is a real trade, and the register must reflect it honestly rather than quietly inheriting the previous "Verified / no license needed" wording.

## 2. Required metadata

Every generated asset carries all fourteen fields. An asset missing any field cannot be accepted.

| Field | Description | Example |
|---|---|---|
| `assetId` | From `ASSET_MANIFEST.md` | `GEM-hero-anime` |
| `filename` | Delivered filename | `hero-anime.webp` |
| `categoryId` | Owning category | `anime` |
| `assetType` | Manifest type | `category-hero` |
| `imageClass` | Canonical class | `CLASS-HERO` |
| `intendedUsage` | Exact UI slot | `Category hub /anime — hero band` |
| `prompt` | The **exact** prompt submitted, verbatim | *(full text)* |
| `negativeConstraints` | The negative block applied | *(full text)* |
| `generationTool` | Tool + model/version | `Google Gemini (<model>, <version>)` |
| `generationDate` | ISO date of generation | `YYYY-MM-DD` *(placeholder until generated)* |
| `provenanceStatus` | `Pending Verification` → `Verified` → (or) `Blocked` | `Pending Verification` |
| `reviewerStatus` | `Not Reviewed` → `Accepted` / `Rejected` / `Revise` | `Not Reviewed` |
| `reviewer` | Who reviewed it | *(name)* |
| `licenseNote` | The honest statement from §1 | *(see §1)* |

Additionally on acceptance: `altText` (hand-written, per `AI_IMAGE_ASSET_BIBLE.md` §8) and `replaces` (the procedural SVG it supersedes, which is **retained**).

## 3. Workflow

```
  ┌─ 1. GENERATE ──────────────────────────────────────────────┐
  │  Submit the exact prompt from GEMINI_IMAGE_PROMPTS.md.     │
  │  Record tool, model/version and date at the moment of      │
  │  generation. Do not paraphrase the prompt.                 │
  └────────────────────────────────────────────────────────────┘
                               ↓
  ┌─ 2. RECORD ────────────────────────────────────────────────┐
  │  Create the metadata record (§2) with                      │
  │  provenanceStatus = Pending Verification,                  │
  │  reviewerStatus  = Not Reviewed.                           │
  │  The file stays OUTSIDE the repository at this stage.      │
  └────────────────────────────────────────────────────────────┘
                               ↓
  ┌─ 3. REVIEW ────────────────────────────────────────────────┐
  │  Run AI_ASSET_REVIEW_CHECKLIST.md in full.                 │
  │  Any single hard-fail ⇒ Rejected or Revise.                │
  └────────────────────────────────────────────────────────────┘
                               ↓
  ┌─ 4. VERIFY TERMS ──────────────────────────────────────────┐
  │  Read the generating platform's terms as of the            │
  │  generation date. Write the licenseNote from §1.           │
  │  Terms unclear or unavailable ⇒ Blocked. Stop.             │
  └────────────────────────────────────────────────────────────┘
                               ↓
  ┌─ 5. ACCEPT ────────────────────────────────────────────────┐
  │  Optimise to the delivered sizes. Write alt text by hand.  │
  │  Commit the file. Add a row to 08_LICENSES.md §1 with the  │
  │  honest status. Update the content JSON `src` — one line.  │
  │  KEEP the procedural SVG it replaced.                      │
  └────────────────────────────────────────────────────────────┘
                               ↓
  ┌─ 6. VALIDATE ──────────────────────────────────────────────┐
  │  npm test — contentValidation.test.ts proves the new       │
  │  asset exists on disk, has alt text and a provenance       │
  │  credit. Visual QA at 375 / 768 / 1440 before it is done.  │
  └────────────────────────────────────────────────────────────┘
```

**Rejection is cheap and expected.** A rejected asset changes nothing: the procedural SVG is still in place and still referenced. There is no half-migrated state.

## 4. Copyright / IP review checklist

Every question must be answered **No** (or N/A) before acceptance. Any **Yes** is a hard fail.

| # | Question | Fail action |
|---|---|---|
| 1 | Does any recognisable real person appear — actor, musician, athlete, streamer, public figure? | Reject |
| 2 | Does any character resemble a character from an existing franchise? | Reject |
| 3 | Is any logo, wordmark, brand mark or trademark visible, even partially or blurred? | Reject |
| 4 | Does it recreate or closely evoke a specific existing poster, album cover, box art or book cover? | Reject |
| 5 | Does any costume, emblem, insignia or colourway match an existing franchise's? | Reject |
| 6 | Is any legible text, lettering or numeral present? | Reject (no prompt in this project requests text) |
| 7 | Is a signature, watermark or artist mark present? | Reject |
| 8 | Does any real-world branded product or packaging appear? | Reject |
| 9 | Does it imitate a *named* living artist's signature style? | Reject |
| 10 | Does a reverse image search surface a near-identical existing work? | Reject and record the finding |
| 11 | Could a reasonable viewer mistake this for official art of a real property? | Reject |
| 12 | Are the generating platform's terms for this output unknown or unverifiable today? | Block — do not commit |

Questions 10 and 12 are the ones most often skipped. Neither is optional here.

## 5. Acceptance criteria

An asset is **Accepted** only when all of the following hold:

- Every metadata field in §2 is populated with a real value — no placeholders, no `TBD`.
- The full `AI_ASSET_REVIEW_CHECKLIST.md` passes with zero hard-fails.
- The IP checklist in §4 is entirely `No`/`N/A`.
- The platform's terms have actually been read on the generation date, and `licenseNote` reflects them without overstatement.
- Hand-written alt text exists and describes the delivered image, not the prompt.
- The asset is measurably better than the procedural SVG it replaces, at an acceptable weight (hero ≤300KB, card ≤80KB delivered).
- It survives its class's crop and downscale (hero: the 5:1 desktop band *and* the near-square mobile crop; portrait: the 4:3 card crop; card: legible at 158px).
- `npm test`, `npm run typecheck`, `npm run lint` and `npm run build` all pass after the swap.
- The replaced procedural SVG is still present in the repository.

## 6. Rejection criteria

Any one of these rejects the asset outright:

- Any `Yes` in §4.
- Anatomy artefacts — malformed hands, distorted faces, extra limbs, duplicated figures.
- Text, watermark or signature present anywhere in frame.
- Critical content outside the class's safe area, so it is lost to cropping.
- Illegible or mushy at the class's smallest render size.
- A bright or busy lower third on a CLASS-HERO, which would compromise hub title legibility.
- Palette drift — more than three hues, or a dominant hue that is not the category accent.
- Style drift — photorealistic, flat-vector, or otherwise inconsistent with the other six worlds.
- Weight above the class budget with no meaningful quality gain over the SVG.
- Provenance or platform terms unverifiable.

**`Revise`** (rather than `Reject`) applies when the concept is right but execution missed — regenerate from the same prompt, or adjust the prompt and record the new prompt verbatim.

## 7. Record location

- **`08_LICENSES.md` §1** — the permanent register. One row per accepted asset, with the honest `licenseNote` from §1. Accepted assets are **not** folded into the existing procedural-SVG batch rows; they are recorded separately, because their rights position is different.
- **`07_AI_USAGE.md`** — the generation event: tool, model/version, date, prompt authorship, and who reviewed.
- **`ASSET_MANIFEST.md`** — regenerated from `scripts/generate-asset-plan.mjs`; tracks planned scope, not acceptance state.
- **`11_DECISION_LOG.md`** — any decision to accept a class of assets, or to abandon the pass.

Nothing is recorded retroactively. If the generation date was not captured at generation time, the asset is `Blocked`.
