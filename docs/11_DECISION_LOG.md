# 11 — Decision Log

Every major technical/product decision, recorded at the time it is made. Nothing here is retroactively rewritten to look cleaner than the reasoning actually was.

| ID | Date | Decision | Rationale | Alternatives Considered | Impact |
|---|---|---|---|---|---|
| D-001 | 2026-09-23 | Use React 18 + TypeScript with Vite as the build tool | SRS explicitly permits ReactJS (p.16); Master Directive assigns React specifically to Claude's responsibility; TypeScript reduces risk across ~76 requirements and a large static JSON schema; Vite gives a fast, backend-free static build appropriate for a no-server SPA | Angular (also SRS-permitted, but not the Master Directive's assigned framework); plain HTML/CSS/jQuery/Bootstrap (SRS-permitted, but weaker for the scale of stateful cross-cutting features like cart/bookmarks/search) | Sets the entire Phase 1 tooling baseline (`02_PRODUCT_ARCHITECTURE.md` §1) |
| D-002 | 2026-09-23 | Use `HashRouter` from React Router for SPA routing | Satisfies CR-004 (SPA, no backend) without requiring server-side rewrite rules; works even on `file://` or a plain static file server for demo purposes, which matters given DR-006/DR-007 (ZIP submission, optional hosting) | `BrowserRouter` with host-specific redirect rules (adds a hosting-dependent configuration step not guaranteed to be available at submission time) | Final routing shape confirmed in `02_PRODUCT_ARCHITECTURE.md` §9 as an open item pending Phase 1/15 hosting decision |
| D-003 | 2026-09-23 | Use Three.js via React Three Fiber, scoped only to the cinematic entry layer, with mandatory WebGL/reduced-motion fallback | Master Directive assigns Claude the Three.js Engineer role and requires the cinematic layer to "support the product rather than replace the required functionality"; a declarative R3F approach keeps the 3D layer composable with React state (skip control, fallback) rather than a separate imperative Three.js app | A separate static (non-3D) landing page (would under-deliver on the Master Directive's cinematic-experience goal); a full site-wide 3D framework (would risk NFR-005 performance and accessibility, and risks becoming "beautiful landing page that fails the SRS") | Governs Phase 4 scope and Phase 13 performance budget (`06_ASSET_BIBLE.md` §4) |
| D-004 | 2026-09-23 | Build a custom, fully in-repo rule-based chatbot engine instead of integrating Tawk.to or Tidio | The SRS *suggests* Tawk.to/Tidio as optional platforms (p.13, p.16) but does not mandate them, and separately *requires* (as a binding constraint, CR-003) that the chatbot not connect to a live external AI service or backend. The Master Directive additionally forbids introducing external runtime dependencies without Director approval. A self-built JSON-driven rule engine satisfies both documents simultaneously with no conflict and no external dependency | Integrating Tawk.to/Tidio (SRS-mentioned but introduces an external SaaS runtime dependency the Master Directive restricts without approval; also typically requires an account/script tag pointing at a third-party service, in tension with "no backend" spirit) | Documented as the resolution to the IR-004 conflict note in `01_SRS_REQUIREMENTS.md` §D; drives Phase 11 implementation |

Copy/UX near the cart (per `03_UX_ARCHITECTURE.md` §8) continues to state explicitly that the cart is temporary/demo-only and clearing browser storage clears it | In-memory only (rejected — Director specified `localStorage`) | Implemented in Phase 1 as `src/stores/cartStore.ts`; documented in `02_PRODUCT_ARCHITECTURE.md` §4/§9 and `05_DATA_SCHEMA.md` §13 |
| D-006 | 2026-09-24 (Director-approved, refined) | Contact Us map architecture: a responsive, client-only Google Maps `output=embed` iframe (no API key, no backend) as the base map, with (a) a "Get Directions" link that opens Google Maps' own directions UI in a new tab pre-filled with FandomVerse's location as destination, and (b) an *optional*, user-initiated browser Geolocation lookup (`navigator.geolocation.getCurrentPosition`) used only to compute a "directions from your location" link — never to auto-collect or transmit location anywhere, since there is no backend to send it to | Satisfies FR-039 (location + GPS) and the Director's refinement: no backend dependency, no exposed secret key, directions capability, explicit-permission-gated geolocation, and a graceful fallback (if geolocation is denied/unavailable, the map and a manual "Get Directions" link still work fully — geolocation is a progressive enhancement, not a requirement to use the page) | Google Maps JavaScript API with a key (rejected — implies key management/billing, out of scope); auto-requesting geolocation on page load without user action (rejected — poor UX and a needless permission prompt; must be user-initiated, e.g. a button) | Documented in `02_PRODUCT_ARCHITECTURE.md` §4, `03_UX_ARCHITECTURE.md` §11, `08_LICENSES.md` §3 |
